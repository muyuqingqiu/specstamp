# sdlc-fix

命令：`codex-sdlc fix`

执行时请：

1. 用户用自然语言说“sdlc 当前需求测试发现”“验收发现”“之前任务完成得有问题”“历史已完成任务有 bug”“回归发现问题”时，写代码前必须先执行 `$sdlc-status` 或读取当前状态分流，不要直接改代码。
2. 分流规则固定为：当前 doing 任务的问题继续当前任务；刚完成或 `ready_for_user_check` 的任务验收不过用 `$sdlc-task-restore`；历史已完成任务后来发现实现问题才用本指令；需求目标变了用 `$sdlc-change`；技术方案错了回 `$sdlc-design`。
3. 只在“历史已完成任务后来发现实现问题”时使用。
4. 当前 doing 任务发现问题时，不用本指令，继续当前任务。
5. 当前任务刚 `$sdlc-task-done` 后用户验收不过时，改用 `$sdlc-task-restore`。
6. 需求目标变了时，改用 `$sdlc-change`。
7. 技术方案错了时，回到 `$sdlc-design`；方案确认后由 `$sdlc-design-accept` 按明确任务影响同步任务计划。
8. 用户明确给出需求和任务时，执行 `codex-sdlc fix REQ-001 T-001 "反馈内容"`。
9. 用户只给出反馈时，按会话上下文找最相关的已完成历史任务；多个高度相关时必须询问用户。
10. 本阶段只插入一个新的修复任务，不恢复旧任务、不改旧任务完成状态、不写代码、不跑测试、不提交代码。
11. 新修复任务要记录来源任务、用户反馈、可能受影响任务和复查点。
12. 如果当前有 doing 任务可能受影响，提醒用户决定先继续当前任务还是先处理修复任务，不要自动暂停。
13. 普通模式完成本指令后必须停下，不要开始修复开发。Goal 模式可以由主 agent 按状态继续下一步。
14. 完成后只推荐 `$sdlc-task REQ-001 T-xxx` 或 `$sdlc-next`。
15. 如果用户是用 `$sdlc-add` 自然语言提交“测试发现 bug + 正确逻辑”，底层会自动分流到修复任务；本指令作为精确手动入口仍保持只插修复任务。
