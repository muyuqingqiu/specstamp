# sdlc-docs

命令：`codex-sdlc docs`

常用写法：`$sdlc-docs REQ-001`

如果客户明确要求把文档提交到 Git，才使用：`$sdlc-docs REQ-001 --commit`

执行时请：

1. 只在需求已经 accepted 后执行；如果需求还没 accepted，先推荐 `$sdlc-regression REQ-001` 或 `$sdlc-accept REQ-001`，不要提前写结束文档。
2. 用户明确指定需求时，执行 `codex-sdlc docs REQ-001`；没有指定时，只在唯一高相关 accepted 需求存在时自动推断。
3. 多个 accepted 需求都相关时，转述候选并让用户选择。
4. 本阶段只生成需求维护文档，不写业务代码、不拆任务、不跑任务测试、不接受新需求。
5. 文档默认写到项目 `docs/guide/` 下，文件风格参考 `docs/guide/设置搜索逻辑梳理.md`。
6. 文档目标是帮助后续开发人员读完就能清楚知道：这轮需求要解决什么、产出了哪些文件、每个文件大概负责什么、整体逻辑线怎么走、验证过什么、后续维护要注意什么。
7. 文档语言必须直白、亲和、少黑话；先给“一句话理解”，再讲入口、流程、数据或状态流、关键文件和维护提醒。
8. 不要把聊天推导、旧方案对比、过程复盘写进文档；只写最终可维护的事实和规则。
9. 如果项目里已有相同主题文档，CLI 会要求加 `--force` 才覆盖；覆盖前先让用户确认。
10. 生成后检查 Git 状态；默认不提交 Git，也不要主动问客户是否提交。
11. 只有客户明确要求“提交文档”“文档也进 Git”“生成后提交”等意思时，才执行带 `--commit` 的 docs 命令，或在文档已经生成后按客户要求单独提交。
12. 最后输出文档路径、文档覆盖范围、Git 是否已提交，以及下一步推荐 `$sdlc-finish`。
