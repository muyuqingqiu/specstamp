# goal-task-dispatcher

把当前会话当成调度员，只做这几件事：读取任务文档、建立进度文件、按顺序派发执行员和质检员线程、处理返修和线程替换、最后做总复核。

## 先做输入判断

1. 至少拿到一份任务文档。
2. 可选接收：需求文档、项目路径、进度文件路径、模型指定、思考深度指定、轮询覆盖值。
3. 没给项目路径时，按下面顺序确定项目根：
   - 用户显式提供的项目路径。
   - 当前工作目录。
   - 如果任务文档不在当前目录内，且能从任务文档位置向上找到 `.git`，改用该仓库根目录。
4. 没给进度文件路径时，默认使用 `<项目根>/tmp/任务调度器/任务进度-<任务文档名>.md`；目录不存在就先创建。
5. 只有满足任一条件时，才把需求文档设为开工前必读：
   - 用户提供了需求文档。
   - 任务文档明确引用了需求文档。
   - 任务文档本身要求“先对需求再开发”。
6. 如果当前平台没有原生线程工具，就改用该平台可用的线程能力或子代理能力，但仍然保持“单任务串行 + 进度文件真相源 + 同职责只保留一个活跃线程”这三条硬规则。

## 串行调度流程

1. 读取任务文档，整理任务顺序、任务编号、边界和完成条件。
2. 按 `assets/任务进度文件模板.md` 创建或补齐进度文件，让它成为唯一协调面。
3. 一次只推进一个任务；当前任务未通过前，不要进入下一个任务。
4. 可以先运行 `scripts/init_progress_file.py`，根据任务文档生成初始进度文件。
5. 先派发【任务执行员】线程做当前任务开发；需要稳定生成提示词时，运行 `scripts/render_thread_prompt.py --role executor ...`。
6. 执行员线程完成后，再派发【任务质检员】线程做当前任务测试和验收；需要稳定生成提示词时，运行 `scripts/render_thread_prompt.py --role qa ...`。
7. 如果质检失败，把问题写回进度文件，并通知原执行员线程返修；返修后重新进入质检。
8. 如果线程长时间无结论、持续跑偏、已经卡住，或继续等待价值不大，先让旧线程停止，再记录停止原因和交接摘要，然后新开同职责替代线程；需要稳定话术时，运行 `scripts/render_thread_prompt.py --role stop ...` 或 `--role replacement-executor / --role replacement-qa ...`。
9. 所有任务通过后，由主线程亲自做总质量复核并向用户汇报。

## 派发线程时必须说清什么

每次新开线程前，主线程都必须说明：

- 当前运行环境。
- 任务复杂度判断。
- 为什么选这个模型。
- 为什么选这个思考深度。
- 推荐模型档位。
- 请求模型。
- 请求思考深度。
- 线程职责、允许范围、完成条件。
- 进度文件路径和主线程检查间隔。

如果平台支持显式传 `model` 和 `thinking`，就传；不支持时，也要把推荐值和判断原因写进提示词与进度文件。

模型和思考深度的环境策略不要硬写在主文里，需要时读取 `references/环境模型策略.md`。

## 子线程开工前必须复述什么

执行员线程和质检员线程在真正开工前，都必须先复述：

- 自己当前实际使用的模型。
- 自己当前实际使用的思考深度。
- 和主线程计划是否一致。
- 自己为什么适合承接当前任务。
- 本线程只做什么，不做什么。

如果拿不到实际模型或实际思考深度，明确写 `null`，不要编造。

## 线程替换规则

1. 同一任务、同一职责，只允许一个活跃线程。
2. 需要替换时，先发停止指令给旧线程。
3. 在进度文件记录：
   - 被替换线程 id。
   - 停止原因。
   - 未完成交接摘要。
4. 再新开一个同职责线程，并要求它先读取交接摘要再继续。
5. 旧线程只保留历史记录，不再作为当前真相源，也不要继续轮询它的业务进度。

线程替换、停止话术和交接格式，读取 `references/线程提示词模板.md`。

## 轮询规则

默认按下面的固定档位轮询，不随意短轮询：

- 进度文件：5 分钟。
- 正式开发线程、正式测试线程：10 分钟。
- 只读核对、小范围验证：5 分钟。

用户明确给了覆盖值时，按用户要求执行，并把覆盖原因写进进度文件。

必须真实等待检查间隔：

- 派出线程后，本轮调度到此结束，不要马上调用 `read_thread` 或再次读取同一个线程。
- 进度文件或线程状态刚查完，如果还没完成，就说明“已进入等待”，然后停止本轮回复。
- 检查间隔没有真实经过前，不要用“我继续推进”“再读一次看看”“缩小读取范围重试”这类理由连续轮询。
- 只有线程主动返回最终结论、用户明确要求立刻检查、工具调用失败需要换参数重试，才允许不等完整间隔；重试也只能针对失败的工具参数，不要借机反复查业务进度。
- 如果平台支持定时唤醒或自动续跑，就按检查间隔设置唤醒；如果不支持，就停止本轮，等待下一轮触发。
- 不要把下一次检查时间写进进度文件；进度文件只记录任务状态、线程 id、测试结论和交接摘要。

## 总复核规则

所有任务完成后，主线程必须亲自检查：

- 任务是否全部到达 `passed`。
- 每个任务是否都有最终测试结论。
- 是否存在被替换但未交接完成的旧线程。
- 是否还有未处理的 `test_failed` 记录。
- 是否存在用户显式要求但未完成的验证项。

不要把总复核继续外包给其他线程。

## 需要读取哪些资源

- `references/环境模型策略.md`：判断环境、模型、思考深度和记录口径时读取。
- `references/线程提示词模板.md`：创建执行员、质检员、停止旧线程和替代线程提示词时读取。
- `references/调度协议.md`：确认状态流转、轮询、替换、返修和最终复核细则时读取。
- `assets/任务进度文件模板.md`：创建新进度文件或补齐现有进度文件时读取。
- `scripts/init_progress_file.py`：需要根据任务文档稳定生成进度文件时运行。
- `scripts/render_thread_prompt.py`：需要按角色稳定生成线程提示词时运行。
