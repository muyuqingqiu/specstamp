# sdlc-add

这个 Skill 对应命令：`codex-sdlc add`

执行时请：

1. 用户想给当前需求补充内容，但没有明确说要走 `$sdlc-change` 或 `$sdlc-plan-add-task` 时，优先用本指令。
2. 默认先由 Codex 判断内容类型、复述需求和预计规划，不要马上调用 CLI。CLI 不做任何自然语言理解或保底分类。
3. 第一次回复先停在“待用户确认”：
   - 说明 Codex 判断这次属于哪一类。
   - 用大白话复述用户真正想补充什么。
   - 说明准备拆成几个任务，每个任务大概做什么。
   - 单独列出验收和回归要求。
   - 给出准备执行的 `codex-sdlc add ...` 命令预览。
   - 明确告诉用户：确认后再实际添加。
4. 只有两种情况可以直接调用 CLI：
   - 用户在同一条消息里明确说“直接添加”“不用复述”“已确认，直接执行”。
   - 上一轮已经完成复述和预计规划，用户本轮回复“确认”“没问题”“按这个执行”等明确确认。
5. 用户确认后，按上一轮整理好的内容调用 CLI，不要再次模板化追问；如果用户改了内容，先按新内容重新复述和规划。
6. 判断类型只分四类：
   - 明确 bug 修复：历史已完成任务或测试发现的问题，需要插入修复任务。
   - 纯执行任务：复查、整理、补测试、补验证、提交边界、任务顺序等不改变需求目标的工作。
   - 需求变更：新增业务规则、新 UI 状态、新展示文案、新跳转目标、新验收口径、截图或设计稿规则。
   - 资料补充：截图、Figma、设计说明、测试账号、环境说明等背景资料，优先用 `$sdlc-material`。
7. 如果用户是在补充一个已有未完成任务的目标、验收、执行方式或依赖，例如“任务目标增加”“T-026 增加要求”“这个任务里发现问题后也要修”，优先改用 `$sdlc-plan-amend-task`，不要登记成需求变更，也不要新建任务；仍然要先复述理解和预计调整，等用户确认后再执行。
8. 调用 CLI 前，把用户原话整理成三部分：
   - 业务变更或任务目标：真正要实现或处理的内容。
   - 验收和回归要求：确保正常、搜索可用、旧行为不受影响、需要回归哪些入口等检查要求。
   - 任务建议：由 Codex 先判断这次变化应该落成几个开发任务，以及每个任务的大白话标题。
9. “确保 xxx 正常”“验证 xxx 不受影响”“回归 xxx”“测试 xxx”这类内容默认属于验收和回归要求，不要当成独立开发任务。
10. 明确 bug 修复时执行 `codex-sdlc add REQ-001 "整理后的 bug 描述" --kind bug --source-task T-001`。原任务编号必须显式传入，CLI 不猜修复来源。
11. 纯执行任务时执行 `codex-sdlc add REQ-001 "整理后的任务目标" --kind task --coverage FR-001`。覆盖的 FR 编号必须显式传入，缺失时 CLI 直接拒绝，不会改猜为需求变更。
12. 需求变更时，必须先由 Codex 判断任务拆分，再执行 `codex-sdlc add REQ-001 "整理后的业务变更" --kind change --task "任务标题||任务目标||FR-001,FR-002"`。验收和回归要求用 `--acceptance` 显式传入。
13. `--kind` 必填。类型不清楚时由 Codex 先向用户问清，不调用 CLI 猜测。
14. 变更草案不会自动生效。下一步只能推荐 `$sdlc-change-accept REQ-001 CHG-xxx` 或 `$sdlc-next`。
15. 本指令不写业务代码、不跑业务测试、不提交 Git。
16. 如果用户同一条消息里给了截图、Figma 链接、设计稿、样式规则或测试资料，先按两步确认规则处理；实际添加后，已经生成任务就用 `$sdlc-material` 关联任务，已经生成 CHG 草案就先让用户确认变更，任务生成后再关联资料。
17. 实际调用 CLI 后，回复要说清楚 Codex 的判断结果、传给 CLI 的业务内容、单独记录了哪些验收和回归要求、是否需要下一步生成执行包，以及下一步是否可以进入 brief。
